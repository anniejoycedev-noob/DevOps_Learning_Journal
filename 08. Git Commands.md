<h2 id="section-1">1. Initializing Git & The `.git` Folder</h2>

<h3>Initializing a Local Repository</h3>
<ul>
  <li><b>Command:</b> <code>git init</code></li>
  <li><b>What it does:</b> Initializes an empty local Git repository.</li>
  <li><b>Interview Question:</b> How do you create/initialize a Git repository, and what happens when you do?
    <ul>
      <li><i>Answer:</i> You use the <code>git init</code> command. Once executed, a hidden folder named <code>.git</code> is created in the directory.</li>
    </ul>
  </li>
</ul>

<h3>What is the `0.git` Folder Responsible For?</h3>
<ul>
  <li>It is the key component of Git used for tracking, logging, and holding local configuration settings.</li>
  <li><b>Security Use Case (Hooks):</b> If a developer unintentionally pushes sensitive credentials or passwords into Git, you can configure scripts inside the <code>.git/hooks/</code> folder (such as a pre-commit hook) to intercept and prevent pushes containing secrets.</li>
</ul>

<h2 id="section-2">2. The Fundamental Git CLI Workflow</h2>

<p>Every developer and DevOps engineer uses this core sequence of commands day-to-day:</p>
<div align="center">
  <pre>
  [ Working Directory ] ──( git add )──► [ Staging Area ] ──( git commit -m "msg" )──► [ Local Repo ] ──( git push )──► [ Remote Repo ]
  </pre>
</div>

<h3>1. Tracking Files (`git add`)</h3>
<ul>
  <li><b>Command:</b> <code>git add &lt;filename&gt;</code> (or <code>git add .</code> to stage all changes).</li>
  <li><b>Why it's needed:</b> Without <code>git add</code>, Git's <code>.dotgit</code> folder won't track the file. Active tracking allows Git to audit changes, manage versions, and safely roll back edits if a file or block of code breaks.</li>
</ul>

<h3>2. Checking Status (`git status` & `git diff`)</h3>
<ul>
  <li><b><code>git status</code>:</b> Inspects the current state, showing untracked files or changes waiting to be committed.</li>
  <li><b><code>git diff</code>:</b> Displays exact line-by-line modifications made to tracked files before staging.</li>
</ul>

<h3>3. Saving Versions (`git commit`)</h3>
<ul>
  <li><b>Command:</b> <code>git commit -m "commit message"</code></li>
  <li><b>Why it's needed:</b> Creates a permanent snapshot entry in the repository history log. If a breaking bug is introduced later, teams can inspect commit logs (using <code>git log</code>) to identify who made the change and roll back to a previously stable version.</li>
</ul>

<h3>4. Pushing Changes (`git push`)</h3>
<ul>
  <li><b>Command:</b> <code>git push</code></li>
  <li><b>The Remote Reference Problem (Interview/Common Error):</b> If you initialize a repository locally via CLI (`git init`), running `git push` immediately will fail because there is no remote reference link. 
    <ul>
      <li><i>Solution:</i> You must clone an existing remote repository, or manually link your local repo using: 
        <pre><code>git remote add origin &lt;repository-url&gt;</code></pre>
      </li>
    </ul>
  </li>
</ul>

<h2 id="section-3">3. Downloading Code: Cloning & Authentication</h2>

<h3>Git Clone</h3>
<ul>
  <li><b>Command:</b> <code>git clone &lt;repository-url&gt;</code></li>
  <li><b>Purpose:</b> Downloads a complete remote repository onto your local machine.</li>
  <li><b>Authentication Mechanisms:</b>
    <ul>
      <li><b>HTTPS:</b> Authenticates using your repository username and account password (or personal access token).</li>
      <li><b>SSH:</b> Authenticates securely using cryptographic public/private key pairs without requiring a password prompt every time.</li>
    </ul>
  </li>
</ul>

<h3>Setting up SSH Keys for GitHub</h3>
<ol>
  <li>Generate keys on your terminal using: <code>ssh-keygen -t rsa</code> (press enter through prompts).</li>
  <li>Navigate to your home directory's hidden SSH folder (<code>cd ~/.ssh</code>).</li>
  <li>Locate the public key file (typically named <code>id_rsa.pub</code>).</li>
  <li>Copy the contents of the public key file.</li>
  <li>Go to your GitHub Account ➔ Settings ➔ SSH and GPG keys ➔ Click <b>New SSH Key</b>, paste the public key, and save.</li>
</ol>

<h2 id="section-4">4. Key Interview Question: Git Clone vs. Git Fork</h2>

<div align="center">
  <table border="1" cellpadding="8" cellspacing="0">
    <tr>
      <th>Feature</th>
      <th>Git Clone</th>
      <th>Git Fork</th>
    </tr>
    <tr>
      <td><b>Definition</b></td>
      <td>Downloads a local copy of a repository onto your machine to work on it.</td>
      <td>Creates an independent server-side copy/replica of a repository under your own account/organization on GitHub.</td>
    </tr>
    <tr>
      <td><b>Use Case</b></td>
      <td>Used to start working on an existing project you have access to.</td>
      <td>Used when contributing to open-source projects (e.g., forking Argo CD or Kubernetes) so you have your own isolated remote copy to modify and push changes to safely.</td>
    </tr>
  </table>
</div>

<h2 id="section-5">5. Branching, Merging, and Cherry-Picking</h2>

<h3>Creating & Switching Branches</h3>
<ul>
  <li><b>Command:</b> <code>git checkout -b &lt;branch-name&gt;</code> (creates and switches to a new branch simultaneously).</li>
  <li><b>Purpose:</b> Isolates experimental or major feature development (e.g., adding division or multiplication functionality) away from the stable main branch.</li>
</ul>

<h3>Merging Strategy 1: Git Cherry-Pick</h3>
<ul>
  <li><b>Command:</b> <code>git cherry-pick &lt;commit_id&gt;</code></li>
  <li><b>How it works:</b> Copies a specific individual commit from one branch and applies it directly to your current branch.</li>
  <li><b>When to use:</b> Ideal when you only need 1 or 2 specific commits. However, it becomes unmaintainable for large features involving thousands of commits.</li>
</ul>

<h3>Resolving Merge Conflicts</h3>
<ul>
  <li><b>Scenario:</b> Occurs when multiple developers modify the exact same lines of code in a file across different branches.</li>
  <li><b>Resolution Process:</b> Open the conflicted file, sit down with the development teams to decide which code block to keep, remove conflict markers, run <code>git add &lt;file&gt;</code>, and commit the resolved changes.</li>
</ul>

<h2 id="section-6">6. Major Interview Question: Git Merge vs. Git Rebase</h2>

<div align="center">
  <pre>
  <b>Git Merge:</b>
  Main Branch:    ─── A ─── B ─── C (Main continues)
                         \       /
  Feature Branch:         ── D ── (Creates a merge commit node; non-linear history)

  ──────────────────────────────────────────────────────────

  <b>Git Rebase:</b>
  Main Branch:    ─── A ─── B ─── C 
                                   \
  Feature Branch:                   ── D' (Replays commits linearly on top of Main)
  </pre>
</div>

<h3>Comparison Table</h3>
<div align="center">
  <table border="1" cellpadding="8" cellspacing="0">
    <tr>
      <th>Feature</th>
      <th>Git Merge</th>
      <th>Git Rebase</th>
    </tr>
    <tr>
      <td><b>History Structure</b></td>
      <td>Creates a <b>non-linear</b> commit history with merge commit nodes. Branch integration paths are preserved visually.</td>
      <td>Creates a clean, <b>linear</b> commit history. It moves/replays your feature branch commits directly on top of the latest main branch history.</td>
    </tr>
    <tr>
      <td><b>Traceability</b></td>
      <td>Exact historical branching timeline is preserved (shows when branches diverged and merged).</td>
      <td>Looks as though all development happened sequentially in a straight line, making audits easier.</td>
    </tr>
    <tr>
      <td><b>When to Use</b></td>
      <td>Best for public/shared feature branches where preserving historical context matters.</td>
      <td>Best for maintaining a clean, straight-line log history on personal or local branches before pushing.</td>
    </tr>
  </table>
</div>
